# GUIDE SaaS 平台角色與取消／爭議建議預設

> Owner Decision：2026-09-02
> 關聯：#41、#12、#42、#43、#46、#48

## 1. 商業模式與平台角色

Midao／新的 GUIDE 後台已轉型為以 **SaaS（訂閱式後台）使用費＋Midao 前台曝光／上架價值** 為主要營收方向。

因此平台不把「代導遊決定旅客退款爭議」當成主要產品或營運職責。

產品角色採：

- Midao 提供訂單、收款狀態、取消、退款、明細、附件、通知、audit（操作紀錄）與政策 snapshot（訂單成交時固定保存的規則）等工具。
- Midao 提供一套容易理解、偏公平、偏低爭議的 **建議預設**。
- 導遊／GUIDE tenant 可依個別 Trip Plan 自行調整商業政策。
- 實際旅客爭議、例外協商與是否提供額外善意退款，原則上由導遊／業者與旅客自行處理。
- Midao 不因提供預設範本就成為退款仲裁者，也不替任一方保證爭議結果。
- 自訂政策仍不得違反適用法律、強制規範、金流商規則或平台安全底線。

## 2. 哪些是可調整建議，哪些是平台底線

### 可由導遊調整

以下屬商業政策，Midao 只提供建議預設：

- 旅客主動取消的退款方式。
- 三段式取消時間區間。
- 訂金／尾款的退款處理。
- 哪些實際第三方成本在合法且已揭露前提下可扣除。
- 特殊日期、客製包團、活動票券等個別方案的取消條件。
- no-show（旅客未出席）、改期、部分旅客取消等處理方式。
- 是否提供比原政策更優惠的善意退款／改期。

導遊自訂後，旅客下單前必須看到實際政策，成交時保存 snapshot；不得事後把已成交訂單改成更不利條件。

### 平台固定底線

以下不是導遊可關閉的偏好：

- 退款與扣款不得出現負數、重複扣款或超過實際已付款金額。
- 系統不可虛構 provider（金流商）沒有實際發生或無可靠資料支持的費用。
- 附件與訂單資料必須做 tenant／order 權限隔離，不得產生永久公開 URL。
- 已成交的價格、取消政策與付款承諾必須使用 snapshot，不得偷偷回寫舊訂單。
- 金流 provider 的真實付款／退款結果必須誠實呈現，不能把「已申請」冒充「已退款」。
- Provider 已確認的重複扣款／重複入帳、超額付款等客觀金流錯誤，系統不得偽裝成正常營收或取消違約金。

## 3. Midao 建議預設

這些是 **default template（建議預設範本）**，不是全平台不可修改的硬規則。

### 3.1 旅客主動取消

沿用 `docs/decisions/2026-08-31-guide-cancellation-policy-config.md`：

- 建議三段式：出發前 8 天以上／4～7 天／0～3 天。
- 預設不是固定百分比沒收，而是：
  `已付款總額（含訂金）－實際不可退成本－金流商實際且確實不退的退款手續費＝建議退款金額`。
- 使用 Midao 建議流程時，每筆不可退成本建議記錄項目＋金額，附件選填。
- Midao 預設顯示透明退款明細；證據附件預設不公開，導遊可選擇分享。
- 導遊可改用自己的合法取消政策與顯示方式。

### 3.2 導遊／業者主動取消整團

Owner 選擇：**A，全額退款。**

Midao 建議預設：

- 旅客已付款金額 **全額退款**，包含已付訂金與尾款。
- 不扣旅客的第三方不可退成本。
- 金流商若有實際且不退的退款／交易手續費，由導遊／業者吸收，不轉嫁旅客。
- 系統建立退款待辦與通知；在 provider 或人工退款真正完成前，狀態只能是 `REFUND_PENDING`（等待退款），不能提前顯示已退款。
- 導遊若要在個別方案使用不同政策，需在下單前清楚揭露，且不得違反適用規範；Midao UI 不把較不利旅客的選項設為預設。

### 3.3 已成團後個別旅客取消，團次仍繼續

沿用 `docs/decisions/2026-09-02-guide-formed-price-protection.md`：

- 其餘旅客維持成交價格，不補差額、不重新計價。
- 取消旅客自己的退款依其成交時政策 snapshot 計算。

### 3.4 未達最低成團而導遊決定取消

Midao 建議視為「業者端未能履約」的情境：

- 建議全額退款旅客已付款金額。
- 金流商實際且不退的手續費建議由導遊／業者吸收。
- 平台不建議套「旅客主動取消」規則扣旅客不可退成本。

此項是 Midao 建議預設，導遊仍可依法規與個別方案條件調整；下單前必須揭露實際規則。

### 3.5 天候、災害、交通中斷等雙方都非故意的情況

Midao 第一建議順序：

1. 先提供免費改期／替代日期。
2. 無法改期時，建議以全額退款作為最少爭議的預設。
3. 若個別方案確實存在已支付且不可回收的第三方成本，導遊可在自訂政策中另行約定，但必須事前揭露並保留明細；Midao 不替導遊自動判定該成本一定可向旅客扣除。

平台不建立「自動判誰有責任」的複雜仲裁引擎。

### 3.6 no-show（旅客未出席）與臨時特殊爭議

Midao 不替所有導遊寫死單一沒收規則。

建議預設：

- 依該 TourOrder 成交時的取消政策 snapshot 顯示建議處理方式。
- 導遊可人工提供部分／全額善意退款或改期。
- 若導遊要設定 no-show 特別規則，放在 Trip Plan 進階設定，旅客下單前看到白話說明。

### 3.7 同一訂單只有部分旅客取消／人數減少

Midao 建議：

- **每人計價**：先依成交時每人價格與該訂單政策計算取消人數的建議退款；留下旅客的成交單價不因別人取消而增加。
- **每團計價**：不要自動把總團價除以新的人數重算每人負擔，也不要自動創造「人數減少補差額」。系統顯示原成交總價與導遊建議退款試算，交由導遊依方案政策處理。
- 若人數減少使整個 Departure 進 `AT_RISK`，仍遵守已成團價格保護：選擇繼續出團時，不增加留下旅客既有 TourOrder 的 `total_amount`／`balance_due`。
- 第一版不建立「把一張 TourOrder 拆成多張新訂單」的複雜流程；以 participant count adjustment（參加人數調整）＋退款紀錄處理即可，除非實際資料模型要求另案。

### 3.8 重複扣款／超額付款

這不是取消政策爭議，而是客觀金流對帳問題。

平台行為：

- Provider 明確確認同一交易被重複 capture（扣款）或旅客實際入帳超過應收時，系統標記為 payment exception（付款異常），不可當作額外營收。
- 建議直接退回可確認的重複／超額部分；不套旅客取消罰則、不扣不可退成本。
- 若 provider 資料不明確，進導遊待辦要求確認，不自動猜測。
- 修正後保留 transaction ledger（交易紀錄）與 audit，不直接改掉歷史使帳務看不出發生過異常。

### 3.9 信用卡爭議款／chargeback

每個 GUIDE tenant 使用自己的 merchant credentials，因此 chargeback（持卡人向發卡行提出交易爭議）原則上由該導遊／業者與自己的金流商處理。

Midao 提供工具但不代替商家應訴：

- 顯示該 TourOrder、付款 transaction、政策 snapshot、通知與退款紀錄。
- 提供可匯出／下載的交易與履約證據摘要，方便導遊交給 provider。
- chargeback 狀態不得直接改寫成「Midao 已賠旅客」或「導遊一定敗訴」。
- 平台不從 SaaS 月費帳戶自動扣款補旅客，也不代墊爭議款。
- 若未來 Midao 成為代收代付方，必須另做 Owner Decision，不能沿用目前責任模型。

### 3.10 退款 API 失敗、等待中或需要人工退款

退款狀態要反映事實：

```text
REFUND_PENDING       已決定／已建立退款待辦，尚未完成
REFUND_PROCESSING    provider 已受理但尚未得到最終結果（若資料模型需要）
REFUNDED             有可靠證據證明退款完成
REFUND_FAILED        provider 明確失敗／需導遊處理（若資料模型需要）
```

第一版不一定要新增全部 enum，但語意必須可表達「尚未完成」與「真正完成」。

- Provider timeout、500、網路錯誤不可自動標記 `REFUNDED`。
- 需要人工匯款時，導遊確認實際完成後才標已退款。
- 失敗或長時間 pending 進 #43 GUIDE 行動收件匣，讓導遊直接重試或標記人工完成。
- Midao 不要求平台管理員逐筆人工核准才能退款。

## 4. 後台 UX 原則

導遊看到的介面應明確區分：

```text
取消／退款政策
● 使用 Midao 建議規則
○ 自行設定
[恢復 Midao 建議]
```

自訂時不要要求導遊理解大量 enum（系統內部代碼）。應提供少量常用模板與清楚的恢復預設功能。

退款處理頁優先回答：

1. 旅客已付多少。
2. 目前套用哪一版政策。
3. 系統依該政策建議退多少。
4. 導遊是否要依自身政策／協商結果調整。
5. 最後實際退多少、是否已真正完成。

介面文案要清楚區分：

- `Midao 建議`：平台提供的快速預設。
- `方案政策`：該導遊真正對旅客使用的規則。
- `本次協商調整`：導遊與旅客針對單筆訂單談定的例外結果。

本次協商若改成比原政策更優惠，可以保存 adjustment reason（調整原因）與 audit；若要改成比成交時政策更不利，系統應警示並要求確認適用規範，而不是安靜覆蓋 snapshot。

不要把 Midao 變成需要人工逐案審核每一筆退款的客服後台。

## 5. Midao 平台不做的事

- 不做跨導遊共享的「奧客／退款爭議黑名單」。
- 不代替導遊與旅客仲裁一般商業爭議。
- 不因退款金額爭議自動從平台 SaaS 帳戶扣款補償旅客。
- 不要求所有導遊使用同一套退款百分比。
- 不以交易抽成／爭議款處理作為主要 GUIDE 營收模型。
- 不建立「平台管理員先核准，導遊才能退款」的中央審批流程。

若未來 Midao 另推出代收代付、履約保證或平台型 marketplace（交易平台）服務，需另做 Owner Decision；不能從目前 SaaS／曝光模式偷偷擴張責任。

## 6. 收費與成長方向

本決策補充 #48：

- 主要付費價值：GUIDE SaaS 後台、自動化、團隊能力與效率。
- 前台收入方向：Midao 曝光／上架／推廣等可清楚分離的服務。
- 平台代建行程、協助營運可作額外服務，但不與旅客退款責任綁在一起。
- 基本訂單、安全、取消、退款紀錄、資料匯出與必要通知屬營運底座，不應因未升級付費而失去處理既有旅客的能力。
- 未來收費設計應優先衡量「替導遊省多少時間／少回多少訊息／提高多少可接單能力」，而不是「Midao 幫多少筆退款爭議仲裁」。

正式價格、前台曝光收費方式與 Production 訂閱扣款仍需 Owner 另行拍板；本文件不授權正式計價或部署。
