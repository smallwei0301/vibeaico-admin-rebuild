# 2026-08-27 Owner Decision — GUIDE 單導遊／多導遊 UI 自動適應

## 決策

GUIDE 模式**不建立「單導遊／多導遊團隊」永久開關**，也不新增 `tenant.guide_mode = SOLO | TEAM` 之類的產品設定。

UI 依租戶目前 `active && bookable` 的導遊數量自動適應：

- **0 位**：進入導遊 onboarding，引導新增第一位可帶團導遊；可先詢問「你本人也會帶團嗎？」來快速建立本人導遊資料。
- **1 位**：自動採單導遊簡化 UX。建立團次時不顯示沒有意義的「主導遊／協同導遊」選擇器；後端仍把唯一導遊正式寫入 `trip_departure_staff`，`role=PRIMARY`。
- **2 位以上**：自動展開團隊 UX，顯示主導遊選擇、協同導遊複選、人員篩選與各導遊可用／忙碌原因。

導遊數量改變時 UI 自動轉換，不要求使用者額外切換模式。停用導遊只影響未來可指派名單，歷史團次、訂單與業績仍保留原人員關聯。

## 為什麼不做模式開關

「單人還是團隊」不是獨立的業務事實，真正的事實是目前有幾位可被指派的導遊。若另做模式開關，會產生「資料已有兩位導遊，但設定仍是單人」的矛盾狀態，後續還會牽動排班、業績、通知與團次指派。

自動適應可以讓單人導遊保持極簡，同時讓團隊在加入第二位導遊時自然長出需要的協作功能，而資料模型始終維持同一套。

## 資料模型原則

UI 可以簡化，但資料不能省略：

- 即使只有一位導遊，團次也必須建立正式 `trip_departure_staff` PRIMARY 關聯，不能靠「反正只有一人」日後猜測。
- 多導遊同樣使用 `trip_departure_staff` 的 PRIMARY／ASSISTANT。
- 停用導遊不刪歷史 assignment。
- 不新增 SOLO／TEAM schema 欄位。

## 行事曆 UX

- 1 位導遊：不顯示「全部導遊」篩選或團隊排班語境，聚焦「我的行程／可接案時間」。
- 2 位以上：顯示團隊人員篩選與每位導遊的可接案／已占用狀態。
- 0 位：行事曆與開團入口都引導先完成導遊設定，而不是產生未指派的新團。

## 未來收費

若未來 SaaS 套餐區分個人版／團隊版，應限制「可啟用的導遊席次數」而不是新增 UI 模式開關。例如個人版 `guideSeats=1`、團隊版 `guideSeats=5`。這是未來商業方案能力，本次只保留架構方向，不在此決策中實作收費限制。
