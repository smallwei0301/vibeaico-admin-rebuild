# 2026-08-27 Owner Decision — 第一輪產品裁示整理

本文件記錄 2026-08-27 逐項討論後由 Owner 明確裁示的產品方向，目的不是取代各領域 canonical 規格，而是保存「為什麼這樣決定」與避免後續 agent 重複請示。

## LINE 老闆通知（#18）

- 最多 3 位接收者。
- 不做「第 4 位開始付費」的人頭席次收費；真正需要付費擴充的是 LINE 推播訊息額度。
- 3 位接收者都可個別設定事件通知開關。
- 旅客自行取消預約屬於要通知的事件。

理由：3 位足以覆蓋老闆／店長／櫃台等常見分工；個別開關可避免不相關人員被訊息轟炸，而不必把席次收費與訊息額度兩種商業模型纏在一起。

## 看診號碼（#20）

病患取消後，當日該號碼直接作廢，不重新發給另一位病患。

理由：同一天若兩位病患都曾持有「8 號」，紙本、LINE 截圖、現場叫號與稽核紀錄容易混淆。少用一個號碼的成本遠低於叫錯人的風險。

## 推薦碼（#24）

MVP 不設有效期限。

理由：原規格雖有「已過期」狀態文字，但沒有定義天數或過期條件。與其憑空發明 30／90 天，不如讓一般推薦碼長期有效；未來若做活動型推薦，再另外設活動期限。

## 平台管理者代登入租戶（#25）

要做，而且是正式 Midao 平台能力，不是除錯捷徑。

未來 Midao 管理者後台可進入指定租戶後台協助查看與修改。必要安全邊界：

- 僅 platform admin 可以啟動。
- 全程留下操作者、目標租戶、時間與寫入操作 audit。
- 租戶可以查看與自己相關的代登入紀錄。
- 代登入畫面持續明示目前操作的租戶。
- 必須有明確退出流程。
- 不得取得租戶密碼、共用密碼或直接冒用租戶憑證。

理由：SaaS 客服未來一定會遇到需要實際協助租戶設定的情境。正確做法不是禁止這項能力，而是把權限與可追責性做完整。

## Google／LINE 第三方登入（#26）

現在就做 Google + LINE Login。

理由：Midao 面向一般導遊，LINE 是自然的登入入口；現在先把長期會使用的登入方式做完整，可以避免未來重構 Auth 流程。平台的 LINE Login channel 必須與每租戶 Messaging API channel 完全分離。

## LINE 平台狀態（#14）

採真實連線檢查，不只顯示「已設定」。

- 伺服器呼叫 LINE `/v2/bot/info`。
- 加短期快取，避免每次換頁都重打。
- LINE 查詢失敗只影響狀態燈，不讓整個後台失效。

理由：Midao 高度依賴 LINE 通知。若 token 已失效但畫面仍綠燈，風險高於多一次非常輕量的 API 查詢。

## 加購與業績（#17／#37）

- 0 元加購允許，負數禁止。
- 業績採 C+：有明確執行人員就歸該人；未指定時繼承預約／團次的主執行人員；另提供「不計個人業績」。
- 旅遊領域：方案不綁導遊，團次才綁主／協同導遊；行程加購目錄與訂單實際加購明細分開。

理由：免費招待也是實際服務內容，應留下資料；而車資、門票等加購不一定屬於任何人的個人業績，因此必須能明確選擇不歸戶。
