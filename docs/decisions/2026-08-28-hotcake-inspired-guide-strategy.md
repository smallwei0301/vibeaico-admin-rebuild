# Owner Decision：HOTCAKE 競品研究後的 GUIDE 產品策略

- 日期：2026-08-28
- 狀態：已裁示
- 適用範圍：`vibeaico-admin-rebuild` GUIDE（嚮導）模式、Midao 旅客前台與相關 SaaS（軟體訂閱服務）規劃
- 研究證據：`docs/research/2026-08-28-hotcake-competitive-analysis.md`
- 正式施工規格：`docs/integration/19-GUIDE-PRODUCT-EXPERIENCE.md`

## 決策摘要

Midao 不複製 HOTCAKE 夯客的全部美業 CRM（顧客關係管理系統）功能，也不以「功能比競品多」為主要競爭方式。

正式產品方向定為：

> **HOTCAKE 的簡單 × Midao 的旅遊領域深度**
>
> **旅客不用問，導遊不用回；系統把訂單、時間、付款、成團與提醒自己接起來。**

## 為什麼這樣決定

公開評論最常肯定夯客的地方，是容易上手、少回訊息、顧客能自助、客服快與價格負擔低。這些好評不是在稱讚資料表多，而是在稱讚「工作變少了」。

Midao 現在已經擁有行程、方案、團次、人員、名額、訂單、付款、成團、通知與報表等底座。下一階段的主要問題不是缺少更多孤立功能，而是這些能力還沒有被壓縮成一條不需要導遊自己補洞的使用旅程。

## 已裁示的產品原則

### 1. 行動優先，而不是圖表優先

GUIDE 首頁先回答：

> 我現在最該處理哪件事？

待確認、待付款、成團不足、退款、今日行程與排班衝突要排在首頁前面；完整圖表放到報表頁。

### 2. LINE-first，但不 LINE-only

旅客可以從 LINE 圖文選單或公開連結完成預約，不必下載 Midao App。沒有 LINE 的旅客仍可用 Email 或手機完成，LINE 不能變成唯一門票。

### 3. 最少必要資料

旅客第一步只填成立訂單所需的 3～5 個必要資料。護照、飲食、接送等非當下必要資訊，改為成立後補填或在真正需要的方案才顯示。

### 4. 逐步展開複雜設定

導遊的高頻操作放在第一層，成團、訂金、季節價格、販售方式等低頻複雜設定放進進階層。底層仍共用同一份資料，不建立簡單版與進階版兩套真相。

### 5. 自動做機械工作，人只做商業判斷

系統自動處理：

- 線上付款成功後更新狀態。
- 計算有效成團人數。
- 達門檻後宣布成團。
- 建立尾款、提醒與派送事件。
- 逾期付款釋放名額。

導遊只在以下情況手動決定：

- 匯款是否真的收到。
- 成團截止仍不足時要成團、延期或取消。
- 已成團後掉破門檻是否繼續。
- 真正退款完成與行程確實完成。

### 6. 旅客風險只做租戶私有防呆

不做跨導遊共享黑名單，不公開旅客信用分數。每個導遊工作室只看自己的客觀履約紀錄、私人標籤與預約政策。

允許針對旅客設定：

- 強制定金。
- 只能先申請再確認。
- 禁止自行下單、需聯絡導遊。
- 熟客例外政策。

所有變更需有原因與 audit（稽核紀錄，也就是誰在何時改了什麼）。

### 7. 報表使用旅遊口徑

GUIDE 報表優先回答：

- 詢問到成交率。
- 熱門行程與方案。
- 平均客單與實收營收。
- 取消、未付款與成團表現。
- 重複旅客與訂單來源。
- 主／協同導遊與 C+ 加購業績。

沒有可靠資料時顯示不足，不得捏造 0 或示範數字。

### 8. 低風險進場，不直接複製競品價格

Midao 不以「一定比夯客便宜」作定位，也不直接照抄 NT$400。

收費方向是：

- 讓新導遊先完成 LINE、建立行程並感受到省時價值。
- 個人／團隊差異用可啟用導遊席次，而不是 SOLO／TEAM 開關。
- 基本交易、安全、退款、Email 與 Telegram 通知不鎖成進階加購。
- Midao 前台上架、平台代建與 SaaS 月費要分開說明。

真正價格與正式上線仍需另行 Owner 決策。

### 9. 票券與點數不是 GUIDE P0 主角

既有票券、點數、會員功能保留，但不以它們做 GUIDE 主要入口。旅遊回流優先考慮跨行程推薦、分享與推薦獎勵。

## 優先順序

### P0

1. #46 LINE-first 自助預約旅程與最少必要欄位。
2. #43 行動收件匣「今天要處理什麼」。
3. #44 旅客風險標籤與訂金／人工確認防呆。
4. #41 + #40 成團、尾款與旅遊行前提醒的可靠自動化。
5. #42 方案快速編輯／進階設定分層。

### P1

1. #45 GUIDE 營運報表。
2. #47 LINE 開通精靈與白話自助診斷。
3. #48 低風險進場收費與產品成長驗證。
4. 平台協助代建與真人支援流程。

### P2

- 跨行程推薦與推薦獎勵。
- 票券、點數、會員分級的 GUIDE 特化。
- AI 經營建議，但必須建立在可信報表上。

## 非目標

- 不把 Midao 變成美容、美髮或一般店家的 CRM 複製品。
- 不為了競品矩陣一次打開所有功能施工，仍須遵守 Issue 依賴與 TEST 序列化。
- 不因這份決策直接執行 Production（正式環境）資料庫修改、正式部署或真實金流／通知。

## 成功判斷

後續不只看「功能是否存在」，還要追蹤：

- 導遊從註冊到完成 LINE 連線的比例與時間。
- 建立第一個可販售方案的比例與時間。
- 旅客從行程頁開始到送出有效訂單的完成率。
- 導遊需要人工回覆才能完成預約的比例。
- 未付款、取消、爽約與通知失敗率。
- 導遊每天處理待辦所需步驟與時間。

這些指標的事件與正式數值由對應 Issue 定義，不能在尚未埋點前捏造基準。
