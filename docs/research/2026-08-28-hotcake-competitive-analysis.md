# HOTCAKE 夯客競品研究與 Midao 機會矩陣

> 研究日期：2026-08-28  
> 研究目的：找出夯客使用者真正稱讚的價值，評估哪些做法適合移植到 Midao GUIDE（嚮導）模式。  
> 本檔是研究證據，不是施工規格。正式產品規則見 `docs/integration/19-GUIDE-PRODUCT-EXPERIENCE.md`。

## 1. 研究範圍與限制

本次檢視來源：

1. 台灣 App Store 的 HOTCAKE 夯客評分與可公開讀取的文字評論。
2. HOTCAKE 官方網站的功能、價格與常見問題。
3. HOTCAKE 教學中心的 LINE、定金、會員標籤、自動關懷等文件。
4. Google Play 與公開搜尋結果；可獨立驗證的長篇評論較少，因此不把搜尋不到的聲量補成數字。

### 評論計數方式

- 研究快照蒐集 **14 則去重後、可明確分類的正向文字評論**。
- 同一則評論可以同時提到「簡單、客服快、價格親民」，所以各主題次數可以重疊，不能相加當成評論總數。
- App Store 的總評分數會隨時間與頁面快取改變；2026-08-28 複驗頁面顯示 **4.8／5，約 144～146 則評分**。此前抓取曾顯示不同總數，因此本研究只把它當市場訊號，不把總評分數寫成永久固定值。
- 「好評次數」只代表本次可取得文字樣本中的提及次數，不代表全部使用者的統計母體。

## 3. 好評背後真正被購買的價值

### 3.1 使用者買的是「不麻煩」

評論反覆出現的生活語言是：

- 不用一個一個回訊息。
- 客人可以自己看剩餘時段。
- 半夜也能自己預約。
- 操作簡單、第一次用也順。
- 客服能快速把問題處理掉。
- 費用不高，願意先試。

因此夯客的護城河不是單一按鈕，而是把預約、空檔、提醒、會員與 LINE 接成一條不需要店家反覆人工補洞的流程。

### 3.2 官方產品承諾也圍繞同一件事

HOTCAKE 官方網站強調：

- 顧客不需下載 App，可從 LINE 完成預約。
- 系統 24 小時自動接單。
- 自動計算空檔與發送提醒。
- 預約、會員、報表、再行銷在同一套系統。
- 真人客服與一對一教學降低導入門檻。

官方價格頁在研究時顯示：

- 體驗方案每月 0 元，會員數達一定門檻後升級。
- 商務方案約 NT$400／每位服務人員／月，並有月費上限。
- 月繳不綁約、0 建置費與 0 開通費。

這些資料支持一個判斷：小型工作者會在意「還沒穩定賺錢前，不要先背高導入成本」。Midao 應學低風險進場，不必把競品價格當成必須照抄的定價。

## 4. 值得借鏡，但不能原樣複製的功能

### 4.1 旅客風險

夯客的評論與教學提到會員標籤、強制定金與黑名單／觀察功能。對 Midao 而言，合理移植方式是：

- 顯示該工作室可驗證的完成、取消、爽約、未付款失效紀錄。
- 允許該工作室自己加私人標籤與備註。
- 可針對旅客強制定金、改成先申請再確認、或禁止自行下單。

**不移植跨不同導遊共享黑名單。** 跨店共享旅客負面評價會帶來隱私、誤判、申訴與資料責任問題，也不符合目前多租戶隔離原則。

### 4.2 會員與點數

美容服務常靠固定週期回訪，同一服務重複購買很自然。旅遊的回購更常是：

> 完成阿里山 → 下次推薦台南文化、花蓮部落或台北夜間導覽。

因此 Midao 已有票券／點數可以保留，但 P0 不以「功能數量」當主賣點。更適合的後續方向是跨行程推薦、旅客分享與推薦獎勵。

### 4.3 LINE 串接

夯客的 LINE 能力很強，但教學仍可看出權限授權、技術者後台、回傳網址等設定成本。Midao 已有 verify（檢查）、Webhook（LINE 把訊息送回系統的入口）、圖文選單與推播底座，應把它包成：

```text
貼入必要資料
→ 自動逐項檢查
→ 白話指出哪裡未完成
→ 發送測試訊息
→ 顯示「LINE 已可接單與通知」
```

導遊不需要先學 Messaging API（LINE 訊息系統接口）才有資格使用。

## 5. Midao 現有底子與缺口

### 已有底子

- `Trip → Plan → Departure → TourOrder` 的旅遊資料樹。
- 固定團次、自選時間、先申請再確認的販售方向。
- PRIMARY 主導遊、ASSISTANT 協同導遊與人員防撞。
- 訂金、付款保留、成團與尾款設計。
- LINE、Email、Telegram 與 notification outbox（待發送通知佇列）規格。
- 顧客標籤、流失風險、訂單來源、報表與 C+ 業績底座。

### 真正缺口

不是再增加一批孤立頁面，而是把現有能力壓成清楚旅程：

1. 旅客從 LINE 到完成預約，不能在中途找不到下一步。
2. 導遊首頁直接告訴他「現在先處理什麼」。
3. 重要狀態要自動推進與通知，只有商業判斷才要求導遊手動決定。
4. 旅客風險要用客觀紀錄與私人政策處理，不用公開羞辱式黑名單。
5. 報表要回答旅遊生意問題，不是把一般 CRM（顧客關係管理系統）換標題。

## 6. 建議優先順序

### P0：先讓接案變安靜

1. LINE-first 自助預約與最少必要欄位。
2. GUIDE 行動收件匣「今天要處理什麼」。
3. 旅客履約風險摘要與強制定金／人工確認。
4. 成單、成團、尾款與行前提醒。
5. LINE 開通狀態白話化。

### P1：讓導遊知道生意發生了什麼

1. GUIDE 營運報表。
2. 開通精靈、自助診斷與平台協助代建。
3. 低風險進場收費與席次設計。
4. 回饋入口與客服改善循環。

### P2：在主流程穩定後再加深回流

- 票券、點數、會員分級。
- 跨行程推薦與旅客推薦獎勵。
- AI 經營建議，但必須先把底層數字算對。

## 7. 研究結論

Midao 不應複製一套穿著登山鞋的美容 CRM。正式方向是：

> **HOTCAKE 的簡單 × Midao 的旅遊領域深度**
>
> **旅客不用問，導遊不用回；系統把訂單、時間、付款、成團與提醒自己接起來。**
