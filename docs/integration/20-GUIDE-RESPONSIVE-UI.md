# 20 — GUIDE 響應式 UI：五大入口與全功能顯示架構

> 本冊是 GUIDE（導遊）模式的 responsive UI（響應式介面：同一套頁面依手機、平板、桌機自動調整）canonical（正式唯一規格）。
>
> Owner 視覺決策：`docs/decisions/2026-08-31-guide-responsive-ui-baseline.md`  
> 五張基準圖：`docs/assets/guide-mobile-ui/`  
> 產品流程與誠實狀態：`docs/integration/19-GUIDE-PRODUCT-EXPERIENCE.md`

---

## 0. 目標

把目前 GUIDE 後台大量側邊欄功能，重新整理成一個「手機先好用、桌機再放寬」的操作系統。

使用者不需要知道系統有幾十張資料表或 route（網址路徑）。第一層只需要知道五件事：

1. **首頁**：現在要做什麼？
2. **團次**：接下來有哪些團？
3. **旅客**：我要找誰、這位旅客目前怎樣？
4. **訊息**：誰在等我回覆？
5. **更多**：低頻設定、方案、收款、團隊、行銷與擴充功能在哪裡？

這是資訊架構重組，不是資料模型重做。

## 1. 全站共用視覺規則

### 1.1 字體與可點擊尺寸

| 元件 | 手機基準 |
|---|---:|
| 頁面主標題 | 28–32 px |
| 區塊標題 | 20–24 px |
| 卡片主文字 | 17–20 px |
| 正文／清單 | ≥ 16 px |
| 次要說明 | 原則 ≥ 14 px |
| 按鈕／列高可點擊區 | ≥ 44 px |
| 底部導航 | 64–72 px + safe area（手機底部安全區） |

不得用 11–12 px 小字把桌機資訊硬塞進手機。

### 1.2 間距

- 手機左右 padding（內距）：16–20 px。
- 卡片 padding：16–20 px。
- 卡片圓角：16–20 px。
- 同區塊列間距：8–12 px。
- 不同區塊間距：16–24 px。
- 每頁首屏原則只出現 2–4 個清楚區塊。

### 1.3 色彩

- Primary（主要色）：深森林綠。
- Secondary（輔助色）：鼠尾草綠／淡綠。
- Surface（卡片底）：白／暖白／米白。
- Attention（需注意）：暖橘。
- Destructive（危險／刪除）：紅。
- 不為每種狀態發明一種新顏色，避免彩虹儀表板。

### 1.4 一張卡只做一件事

卡片應回答其中一個問題：

- 有什麼要處理？
- 下一團是什麼？
- 這位旅客是誰？
- 這則訊息要不要回？
- 這個設定是否正常？

不要在同一張卡同時塞營收、旅客、付款、導遊、通知健康、行銷數字。

## 2. 五大父層級導航

### 手機

固定底部：

`首頁｜團次｜旅客｜訊息｜更多`

### 平板

可維持底部導航，或改為窄版側 rail（側邊圖示列）；父層級仍是同五項。

### 桌機

可以使用左側 sidebar（側邊欄），但第一層仍只能是同五個父層級；點開父層級後再顯示次層功能。

**禁止**桌機因空間變大就重新把所有二十幾個 leaf（葉節點／單一功能）永久攤平。

## 3. 首頁

基準：`01-home.webp`

### 3.1 首屏順序

1. 品牌／使用者區。
2. 簡短問候 Hero（歡迎區），不可比待辦更搶戲。
3. **今天重點**，最多三類。
4. **接下來出發**，預設最多三團。
5. **本週行程概覽**。
6. **快速操作**，最多三個。
7. 通知／連線健康摘要，可折疊或放頁尾。

### 3.2 今天重點

由真實狀態推導，優先序沿用 19 分冊與 #43：

- REQUEST 待確認。
- 旅客訊息待回覆。
- 待收訂金／尾款。
- 成團不足需決策。
- 已成團後掉到門檻以下。
- 待退款。
- 導遊衝突／缺 PRIMARY。
- 確實需要使用者處理的通知失敗。

首屏最多顯示三類，其他進「查看全部」。

### 3.3 禁止

- 首頁先塞八張 KPI（關鍵數字）卡。
- 沒有真實資料時顯示示範營收／回覆率。
- 把低頻設定放在首頁主區。

## 4. 團次

基準：`02-departures.webp`

### 4.1 這個父層級負責什麼

Canonical parent（正式父層級）為 **團次**：

- `/tenant/calendar`
- `/tenant/tour-orders`
- `/tenant/trips`

其中：

- Calendar（行事曆）是手機團次入口。
- Tour Orders（旅遊訂單）從團次卡／團次詳情進入，必要時提供次層清單。
- Trips / Plans（行程／方案）屬團次領域的商品設定；「更多」可提供快捷入口，但不建立第二套資料。

### 4.2 GUIDE 行事曆

**不得使用商店模式的精細每小時直式時間軸作為 GUIDE 手機主要畫面。**

手機優先：

- 月視圖：日期 + 是否有團／團數。
- 週視圖：七天 + 每日團數。
- 選日期後：直接列該日 Departure（團次）。
- 精確開始／結束時間只放在團次卡與詳情。

狀態切換建議：

`即將出發｜募集中｜已完成`

必要時再加篩選，不在第一層塞十種 status（狀態）。

### 4.3 團次卡

至少顯示：

- 行程／方案名稱。
- 日期。
- 必要時時間。
- 有效旅客數／容量。
- 成團狀態。
- PRIMARY 主導遊；多導遊時詳情再展開 ASSISTANT 協同導遊。
- 一個主要下一步。

## 5. 旅客

基準：`03-travelers.webp`

Canonical parent：`/tenant/customers`

### 5.1 第一層

- 搜尋：姓名、電話、Email、行程／訂單關聯。
- 快捷篩選：全部、今日出發、待回覆、高回訪；實際顯示項目必須由真實資料可算出。
- 清單每列只顯示：姓名、最重要狀態、最近／即將行程。

### 5.2 旅客詳情

逐步展開：

1. 聯絡方式。
2. 即將／歷史 TourOrder。
3. 客觀履約紀錄：完成、旅客取消、導遊取消、爽約、未付款失效。
4. 租戶私有標籤與預約政策（#44）。
5. 啟用功能時才出現會員、點數、票券。

禁止跨 tenant（不同導遊工作室）共享黑名單或主觀信用分數。

---

## 6. 訊息

基準：`04-messages.webp`

Canonical parent：`/tenant/chat`

### 6.1 第一層

第一屏只回答「誰在等我回？」：

- 今日待回覆卡，可列前 1–3 筆。
- Tabs（分頁）：全部／旅客訊息／系統通知。
- 搜尋。
- 下方訊息清單。

### 6.2 訊息與設定分開

訊息頁是工作收件匣，不把這些設定塞進同一頁：

- LINE channel 設定。
- Rich Menu（圖文選單）。
- keyword replies（關鍵字回覆）。
- AI assistant（AI 客服）。
- 通知規則。

以上統一放「更多 → LINE 與自動化／通知」。訊息頁可以提供「設定」快捷連結，但不重複一套設定表單。

### 6.3 真實狀態

- API 回成功不可冒充「旅客已讀」。
- 未讀、待回覆、已讀必須有正式定義。
- 系統通知走 #40 notification outbox（待發送通知佇列）／delivery ledger（各通道發送紀錄）時，畫面只顯示後端真的知道的狀態。

## 7. 更多

基準：`05-more.webp`

「更多」不是垃圾桶，而是低頻功能的分組目錄。

### 7.1 頁首

- 導遊／工作室身分。
- 編輯個人資料。
- LINE／Email／Telegram（若已啟用）的連線健康摘要。

### 7.2 功能分組與現有 route 映射

#### A. 行程與營運

- 方案管理 → `/tenant/trips`
- 導遊／團隊 → `/tenant/staff`
- 報表 → `/tenant/reports`
- 行事曆同步 → `/tenant/calendar-sync`

#### B. 收款

- 收款設定 → `/tenant/payment-methods`
- 商品訂單 → `/tenant/product-orders`（PRODUCT_SALES 啟用時）
- 商品 → `/tenant/products`（啟用時）
- 庫存 → `/tenant/inventory`（啟用時）

#### C. 旅客經營

- 旅客標籤／政策 → Customers 對應設定區
- 會員等級 → `/tenant/membership-levels`
- 票券 → `/tenant/coupons`
- 點數 → `/tenant/points`

#### D. LINE 與自動化

- LINE 設定 → `/tenant/line-settings`
- Rich Menu → `/tenant/rich-menu-design`
- 關鍵字回覆 → `/tenant/keyword-replies`
- AI 客服 → `/tenant/ai-settings`
- 通知設定 → `/tenant/settings` 對應通知區，後續可有專頁但不可複製資料模型

#### E. 曝光與行銷

- 推廣 → `/tenant/promote`
- 活動 → `/tenant/campaigns`
- 行銷推播 → `/tenant/marketing`
- 推薦 → `/tenant/referrals`
- 公開頁設計 → `/tenant/shop-design`
- 作品集 → `/tenant/portfolio`

#### F. 平台與帳號

- 店家／系統設定 → `/tenant/settings`
- 功能商店 → `/tenant/feature-store`
- 支援／回報問題 → 現有 report issue / support 能力
- 贊助 → `/tenant/donate`

### 7.3 顯示規則

- 高頻項目放上方。
- 低頻群組可折疊。
- 未啟用功能依既有 Feature Store（功能商店）規則顯示「未啟用」或升級入口；不可顯示成可用後再失敗。
- 使用者在三次點擊內應可抵達任何 GUIDE 可見功能。

## 8. 桌機與平板怎麼放大

### 8.1 不等於把字變小、一次塞更多

桌機可以：

- 兩欄卡片。
- 左側父層級 + 右側次層選單。
- 清單與詳情雙欄。

但仍須保留：

- 同樣的大標題層級。
- 同樣五個父層級。
- 同樣的狀態用字與顏色。
- 同樣「先重要、後進階」的資訊順序。

### 8.2 建議斷點

斷點（breakpoint：畫面寬度到某值時切換布局）由現有 CSS 系統統一實作，至少驗證：

- 375 px 手機。
- 390 px 手機。
- 430 px 大手機。
- 768 px 平板。
- ≥ 1024 px 桌機。

不得有橫向 overflow（內容超出畫面形成不必要水平捲動）。

## 9. 共用 UI 元件

施工時先抽共用元件，避免五頁各長出一種設計：

- `GuideMobileHeader`：品牌、身分、通知／帳號。
- `GuideBottomNav`：五大入口。
- `GuideSectionCard`：白底大卡片。
- `GuideStatusPill`：狀態小標籤，集中管理顏色與文案。
- `GuideActionCard`：今天重點。
- `GuideDepartureCard`：團次卡。
- `GuidePersonRow`：旅客／訊息人物列。
- `GuideWeekStrip`：七天團數摘要。
- `GuideMonthSummary`：非小時制月曆。
- `GuideSettingsGroup`：更多頁設定群組。
- `GuideEmptyState`：真實無資料狀態。

元件名稱可按 repo 慣例調整，重點是共用語意，不是硬照名稱建立。

Design tokens（設計變數：統一保存字級、間距、圓角、陰影、顏色）必須集中，不准每頁散寫近似數字。

## 10. 遷移策略

### Phase A — 介面基礎

- 建 GUIDE responsive tokens 與共用元件。
- 建五大父層級 AppShell（全站外框）。
- 不改 API／DB。

### Phase B — 導航

- 手機固定五底部入口。
- 平板／桌機用相同五父層級重組現有 NAV。
- 保留既有 route，所有舊 deep link（直接開特定頁面的網址）仍可用。

### Phase C — 五頁

依序：首頁 → 團次 → 旅客 → 訊息 → 更多。

### Phase D — 次層功能套版

所有 GUIDE 可見的既有頁面逐步套用同一字級、間距、表單、卡片、狀態與 responsive 規則。

### Phase E — 收尾

- 移除 GUIDE 舊的密集導覽樣式。
- 補無障礙、鍵盤、螢幕閱讀器與大字級測試。
- 完整 E2E（端到端瀏覽器測試）。

## 11. 驗收標準

### 導航與功能覆蓋

- [ ] GUIDE 可見的每個現有功能都能從五大入口之一，在 ≤3 次點擊內抵達。
- [ ] 舊 deep links 仍可直接開啟，不因導航重構 404。
- [ ] 0／1／2+ 導遊自動 UI 規則不回歸。
- [ ] Feature Store 的啟用／未啟用狀態不被新 UI 繞過。

### 手機與響應式

- [ ] 375／390／430 px 無不必要水平捲動、裁字、重疊、超出卡片。
- [ ] 768 px 與桌機版維持相同五父層級。
- [ ] 正文 ≥16 px；次要文字原則 ≥14 px；觸控目標 ≥44×44 px。
- [ ] 作業系統放大字體後，主要操作仍可完成。
- [ ] 底部導航不被 iPhone／Android 安全區遮住。

### 五張基準頁

- [ ] 首頁符合 action-first（行動優先），最重要待辦在圖表之前。
- [ ] 團次頁手機沒有小時級直式行事曆。
- [ ] 旅客頁搜尋／篩選／狀態在一屏可理解。
- [ ] 訊息頁待回覆優先，設定不混進收件匣。
- [ ] 更多頁功能分組完整，沒有失蹤的 GUIDE 可見 route。

### 誠實與資料

- [ ] 不把基準圖示範數字、人名、照片寫成正式假資料。
- [ ] 所有數字與 badge（提示數字）來自正式 API／真實狀態。
- [ ] 沒資料就顯示空狀態，不造假。
- [ ] 付款／成團／通知 wording（用字）符合 18／19 分冊。

### 工程

- [ ] i18n（多語系字典）完整，不在頁面新增散落硬編碼文案。
- [ ] typecheck（型別檢查）全綠。
- [ ] unit（單元測試）全綠。
- [ ] integration（整合測試）全綠。
- [ ] build（正式編譯）成功。
- [ ] E2E（端到端瀏覽器測試）涵蓋五大入口與主要次層。
- [ ] Playwright（瀏覽器自動化）保存五個父層級的穩定截圖證據，至少涵蓋 390 px 手機與桌機。

---

## 12. 明確禁止

- 不另建 GUIDE 專用第二套 Trip／Order／Customer 資料表只為配合 UI。
- 不把五張圖片直接切圖當成網頁。
- 不追求逐像素複製而犧牲真實資料、長文字與無障礙。
- 不用極小文字補救資訊過多。
- 不把 GUIDE 日曆改回美業式每 15／30 分鐘時段牆。
- 不在每個頁面各自定義一套 status 顏色。
- 不因桌機變寬就恢復舊的全功能平鋪選單。
