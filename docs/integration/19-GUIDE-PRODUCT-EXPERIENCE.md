# 19 — GUIDE 產品體驗：簡單接案、行動收件匣與旅客自助

> 本冊是 GUIDE（嚮導）產品體驗的 canonical（正式唯一規格）文件。  
> 旅遊資料與付款狀態仍以 10、17、18 分冊為準；本冊規定使用者如何看見、理解與完成這些流程。  
> 決策背景：`docs/decisions/2026-08-28-hotcake-inspired-guide-strategy.md`。  
> 競品證據：`docs/research/2026-08-28-hotcake-competitive-analysis.md`。

## 0. 北極星

Midao 不是一般 CRM（顧客關係管理系統），而是台灣獨立導遊的接案助手。

產品承諾：

> **旅客不用問，導遊不用回；系統把訂單、時間、付款、成團與提醒自己接起來。**

衡量功能好壞時，先問：

1. 旅客是否能不私訊來回就完成下一步？
2. 導遊是否一打開後台就知道先處理什麼？
3. 系統是否自動完成客觀、重複、可計算的工作？
4. 狀態是否誠實，沒有把「已送出」冒充「已成立」？
5. 手機上是否能在合理步驟內完成？

如果一項功能只增加欄位、頁面或圖表，卻沒有減少人工動作，不算完成本冊目標。

## 1. 核心設計原則

### 1.1 LINE-first，不是 LINE-only

- LINE 圖文選單與訊息連結是 GUIDE 的主要入口。
- 旅客不需下載 Midao App。
- 公開網址必須能在 LINE 內建瀏覽器與一般手機瀏覽器操作。
- 沒有 LINE 的旅客仍可用 Email 或手機完成；LINE 不能是唯一驗證或通知管道。

### 1.2 先選方案，再顯示該方案能買的日期／時間

同一行程可能有固定小團、私人包團、客製申請三種方案。旅客先選方案，系統再依 Plan 的販售方式顯示：

- 固定團次。
- 導遊真正可接案的時間。
- 可送出申請的候選時間。

不得先丟一個大月曆，再讓旅客猜哪個方案適用。

### 1.3 最少必要資料

第一個資料頁原則上只收 3～5 個必要項目：

- 聯絡人姓名。
- 至少一種可聯絡方式。
- 參加人數。
- 方案當下真正需要的必要問題，原則上不超過 2 個。

護照、飲食、接送、保險、完整旅客名單等資料，若不是成立訂單當下必要，改成訂單成立後補填或只在需要的方案出現。

### 1.4 Progressive disclosure（逐步展開）

對導遊：

- 高頻的名稱、內容、價格、是否販售放第一層。
- 成團、訂金、販售方式、季節價格等放進階層。

對旅客：

- 只在下一步真的需要時顯示付款、成團或補資料內容。

介面可以分層，資料模型、API（系統之間交換資料的接口）與狀態不能分裂成兩套。

### 1.5 Action-first（行動優先）

GUIDE 首頁先顯示需要處理的事情，不先用大面積圖表占滿首屏。

完整數據分析放報表頁；首頁只保留會改變今天行動的摘要。

### 1.6 Truthful state（誠實狀態）

以下文案不可混用：

| 真實狀態 | 可以顯示 | 不可顯示 |
|---|---|---|
| REQUEST 已送出、導遊尚未接受 | 已送出申請，等待導遊確認 | 預約成功 |
| 金流頁已建立、尚未付款 | 等待付款 | 已付款 |
| 只付訂金 | 訂金已付，等待成團／尾款 | 已付清 |
| 已達最低成團 | 已成團，仍可報名 | 客滿 |
| Email 供應商接受寄送 | 已交給 Email 服務商 | 已送達／已讀 |
| Telegram／LINE API 回成功 | 平台已接受訊息 | 使用者已讀 |

### 1.7 不新增重複真相

- 待辦由 TourOrder、Departure、付款、通知等真實狀態推導，不另建一套手動同步的訂單狀態。
- 旅客風險由真實事件與租戶私有政策組成，不新增跨店共享評分。
- 報表從正式資料計算，不在前端保存另一份統計真相。

## 2. 旅客自助旅程

施工 Issue：#46；底層依賴 #12、#37、#40、#41。

```text
LINE 圖文選單／公開網址
→ 行程
→ 方案
→ 日期／時間
→ 最少必要資料
→ 付款或送出申請
→ 真實完成頁
→ 訂單查詢、通知與後續補資料
```

### 2.1 固定團次

旅客至少看見：

- 日期與開始時間。
- 剩餘名額。
- 最低成團人數、目前有效成團人數、尚差幾人。
- 成團截止日。
- 已成團但尚可加入、客滿、截止待決等不同狀態。

### 2.2 自選時間

- 只顯示至少有一位合格導遊真正可用的候選時間。
- 成交前後都由後端重新檢查 availability（可接案狀態），不能只相信畫面。
- 成交時自動建立 PRIVATE Departure（私人團次）與 PRIMARY 主導遊。

### 2.3 先申請再確認

- 送出申請時不鎖導遊時間。
- 畫面明確說明「尚未保留時段」。
- 導遊接受時原子重查；成功者才取得時段並進付款。
- 同時間其他申請需收到清楚結果或替代時間，不可無聲消失。

### 2.4 完成頁

至少顯示：

- 訂單或申請編號。
- 目前狀態。
- 已付、待付與期限。
- 是否已成團；未成團時的進度與最晚通知日。
- 何時提供集合資訊。
- 查看訂單與聯絡導遊入口。

## 3. GUIDE 行動收件匣

施工 Issue：#43。

### 3.1 首頁分區

1. **立即處理**：已逾期、會阻止付款／出團、退款或履約。
2. **今天處理**：期限在租戶今天內。
3. **接下來**：未來數日的行程與提醒。

### 3.2 第一版待辦來源

- 待接受／拒絕的 REQUEST。
- 等待訂金、尾款或付款即將到期。
- `REVIEW_REQUIRED`：成團截止不足。
- `AT_RISK`：已成團後人數跌破門檻。
- `REFUND_PENDING`：退款尚未完成。
- 今日／明日團次。
- 導遊未指派、時間衝突或不可履約。
- notification delivery 永久失敗，且確實需要租戶處理。

### 3.3 每張卡片

至少包含：

- 白話原因。
- 行程／團次或旅客。
- 截止時間。
- 一個主要操作。
- 直接開到對應資料的深層連結（deep link）。

無待辦時顯示誠實空狀態，不放示範資料。

## 4. 旅客履約風險與預約政策

施工 Issue：#44。

### 4.1 禁止跨租戶黑名單

- 不共享不同導遊對旅客的負面評語。
- 不提供公開信用分數。
- 不讓平台搜尋其他租戶的私人備註。

### 4.2 顯示客觀事實

至少分開：

- 已完成。
- 旅客取消。
- 導遊／系統取消。
- 爽約。
- 未付款逾期失效。
- 待退款／已退款。

不同原因不可混成一個紅色分數。

### 4.3 租戶私有政策

建議等價策略：

- `DEFAULT`：沿用方案政策。
- `FORCE_DEPOSIT`：強制定金。
- `REQUEST_ONLY`：只能送出申請，由導遊確認。
- `BLOCK_SELF_SERVICE`：不可自行下單，需聯絡導遊；後台仍可代建。
- 是否加入熟客免訂金，需明確權限與警示。

變更需記錄原因、操作者、時間；旅客端只顯示中性完成方式，不暴露內部標籤。

## 5. 旅遊通知節奏

派送底座：#40；成團與付款事件：#41。

### 5.1 重要事件

至少建立可重試、不可重複的通知事件：

- 申請已收到。
- 導遊接受／拒絕／時段已被取得。
- 等待付款。
- 訂金已收。
- 已成團。
- 尾款開放與即將到期。
- 未成團取消與退款進度。
- 出發前 3 天。
- 出發前 1 天。
- 當日集合、導航與聯絡方式。
- 團次取消、延期或集合資訊變更。

### 5.2 通道

- LINE 適合即時旅客通知，但受官方額度與好友綁定限制。
- 免費方案至少有基本 Email + Telegram；Telegram 主要可用於導遊／管理者，不假設所有旅客都有 Telegram。
- 重要通知必須進 notification outbox（待發送通知佇列）與 delivery ledger（逐通道派送帳本），失敗可重試與追蹤。

### 5.3 內容

每則通知只回答：

1. 發生什麼事。
2. 旅客現在需不需要做事。
3. 截止時間。
4. 一個主要按鈕。

不要把整張訂單資料塞成訊息牆。

## 6. LINE 開通精靈

施工 Issue：#47。

導遊畫面用白話呈現以下檢查：

- 帳號資料可讀。
- LINE 把訊息送回 Midao 的網址正確並啟用。
- 自動回覆模式不衝突。
- 圖文選單已發布或尚未發布。
- 推播額度可查。
- 使用該租戶自己的設定發送測試訊息。
- 測試派送留下 #40 定義的紀錄。

技術錯誤可以留在詳細資訊，但主要文案要說明使用者能做什麼。不得 fallback（偷偷改用）平台共用憑證。

## 7. GUIDE 營運報表

施工 Issue：#45。

### 7.1 第一階段

- 訂單狀態分布。
- 實收營收。
- 平均客單。
- 取消率與取消原因。
- 未付款率。
- 成團率與未達門檻率。
- 熱門行程／方案，分訂單、人數與實收營收排序。
- 訂單來源。
- 重複旅客。
- PRIMARY／ASSISTANT 與 C+ 加購業績。

### 7.2 第二階段

REQUEST 詢問事件完成後，再顯示：

- 詢問 → 接受 → 付款 → 成交漏斗。
- 拒絕、時段被搶走、未付款等流失原因。

沒有可靠事件前，不顯示假成交率。

### 7.3 UI

- 摘要先於圖表。
- 每個指標顯示白話定義。
- 數字可下鑽到訂單清單。
- 手機版一張圖一個區塊，不塞成密集企業儀表板。

## 8. 方案管理與平台代建

施工 Issue：#42；管理者代登入依 #25。

### 8.1 快速編輯

- 名稱。
- 簡短內容。
- 基本價格／兒童價格。
- 是否販售。
- 公開頁預覽。

### 8.2 進階設定

- 每人／每團計價。
- 人數、團型、最低成團。
- 固定團次／自選時間／先申請再確認。

- 季節價格與其他低頻規則。

Midao 協助代建的方案只標記來源，導遊仍可編輯；不建立平台版與導遊版兩套 Plan。

## 9. 收費與成長驗證

研究施工 Issue：#48。任何正式價格與計費上線仍需 Owner 另行裁示。

原則：

- 低風險進場，不承諾一定比競品便宜。
- 個人／團隊依 active+bookable 導遊席次，不做 SOLO／TEAM 開關。
- 基本交易、安全、退款、Email、Telegram 通知不能被進階付費功能鎖住。
- SaaS 使用費、Midao 上架費與平台代建服務分開呈現。
- 方案到期不破壞已成立訂單與歷史資料。

### 9.1 驗證用三層方案（不代表正式售價）

| 層級 | 適合誰 | 驗證期可用範圍 | 達到限制時 |
|---|---|---|---|
| 免費／試用 | 還沒穩定接單、想先確認 LINE 與預約是否省時間的導遊 | 1 位 active+bookable 導遊；以「有效旅客或有效訂單」作主要限制實驗，天數與已發布有效行程數作比較組；保留核心接單、付款處理、交易／安全／退款通知，以及基本 Email、Telegram 通道 | 不鎖整間後台；仍可看與匯出資料、處理已成立或付款中的訂單。在新增動作會超過該輪旅客、訂單或已發布行程限制前顯示升級說明 |
| 個人 | 一位導遊自己接案與帶團 | 1 位 active+bookable 導遊；提高有效旅客、訂單與行程用量；提供完整日常接單工具 | 嘗試啟用第 2 位可帶團導遊時說明團隊方案；既有資料與歷史人員不消失 |
| 團隊 | 兩位以上導遊共同接案 | 依 active+bookable 導遊席次採階梯驗證；同一套功能與資料模型，不設 SOLO／TEAM 開關 | 超過席次時只阻止「再啟用一位可接案導遊」，不影響既有訂單、付款與資料檢視 |

限制實驗一次只改一個主要變數。第一輪比較「有效旅客數」與「有效訂單數」何者最能
讓導遊先感受到成交價值；第二輪可比較「使用天數」與「已發布且至少有一個可售方案的
有效行程數」。草稿行程不計數，避免用整理中的內容製造付費壓力。`active+bookable` 席次只
計算目前啟用且可被指派帶團的人員，停用人員與歷史指派不占新席次，也不得失去紀錄。

### 9.2 三種費用分開呈現

| 項目 | 買到什麼 | 是否綁在 SaaS 方案內 |
|---|---|---|
| SaaS 使用費 | 後台接單、付款狀態、行事曆、通知與營運工具 | 是；正式價格待 Owner 決策 |
| Midao 前台上架費 | 在 Midao 旅客前台曝光、審核與上架服務 | 否；獨立揭露，不假裝月費已包含 |
| 平台代建服務 | 由 Midao 協助建立或整理行程資料 | 否；一次性或服務型費用另列，導遊仍擁有並可編輯資料 |

對外不得用一個模糊總價把三者混在一起。尚未選購上架或代建，不影響導遊使用自己
後台；反過來，購買代建也不等於永久取得 SaaS 或上架資格。

### 9.3 到期、降級與資料保留

| 狀況 | 仍可做 | 暫時限制 | 回復方式 |
|---|---|---|---|
| 試用／免費額度用完 | 登入、查看與匯出資料、處理已成立訂單、收款／退款、接收基本交易與安全通知 | 新增超過限制的有效訂單或旅客 | 升級後立即恢復新增，不搬移資料 |
| 個人版停用或到期 | 同上；唯一導遊的歷史團次與業績仍可查 | 建立新的付費能力或超額用量 | 續訂後沿用原資料與設定 |
| 團隊版降為個人版 | 所有歷史人員、指派、訂單與業績可看；已成立團次可履約 | 只能保留 1 位 active+bookable 導遊；不得新增超額席次 | 管理者選擇保留的啟用導遊，或恢復團隊席次 |
| 取消訂閱 | 到當期結束前照常使用；期末後套用上述保留規則 | 不得只因訂閱到期就刪除已付旅客、歷史訂單、付款或通知帳本 | 重新訂閱時的「原設定立即恢復保證期」待 Owner 決策；在資料保留政策拍板前不得實作自動刪除 |

任何到期處理都不得讓付款中的訂單、已成立訂單或已付旅客失去處理入口。基本 Email、
Telegram、交易、退款與安全通知永遠屬於基礎能力；LINE 額度或進階自動化可另行設計，
但不能把重要通知靜默丟棄。

### 9.4 事件與報表定義

| 指標 | 事件／時間點 | 成功判定 |
|---|---|---|
| 註冊 → LINE 完成連線率 | `guide_registered` → `line_connection_verified` | 憑證、Webhook 與該租戶測試訊息檢查皆通過；只貼入 Token 不算 |
| 建立第一個方案率 | `guide_registered` → `first_trip_plan_published` | 至少一個可供旅客選擇的方案發布；草稿不算 |
| 第一筆詢問／訂單所需時間 | 註冊時間 → `first_inquiry_received` 或 `first_valid_order_created` | 分開呈現詢問與有效訂單，不混成同一數字 |
| 免費 → 付費轉換 | `plan_upgrade_started` → `subscription_activated` | 付款供應商確認後才算，不以點擊升級按鈕冒充 |
| 升級原因 | `upgrade_prompt_viewed`／`subscription_activated` 的 `reason` | `GUIDE_SEAT`、`ORDER_USAGE`、`TRAVELER_USAGE`、`PUBLISHED_TRIP_USAGE`、`ADVANCED_NOTIFICATION`、`MIDAO_LISTING`、`PLATFORM_ASSISTED`、`OTHER` |
| 取消後資料回復率 | `subscription_cancelled` → `subscription_reactivated` | 同一租戶在保留期內恢復，資料仍完整 |

報表同時保留分母。例如「LINE 連線率」需顯示完成數／符合資格註冊數，沒有足夠樣本時
顯示資料不足，不顯示看似精確的 0%。事件不可含 Token、旅客證件或付款秘密。

### 9.5 升級提示與對外白話文案草案

- 免費入口：`先把 LINE、行程和接單流程跑順，真的開始接單後再升級。`
- 個人方案：`一個人帶團也能把詢問、付款、成團和提醒放在同一處。`
- 團隊方案：`多位導遊一起接案，各自的時間、團次和業績不打架。`
- 席次提示：`目前可啟用 1 位帶團導遊。要讓第 2 位也能被旅客預約，請查看團隊方案。`
- 用量提示：`既有訂單不受影響。升級後可以繼續接受新的預約。`
- 到期提示：`你的資料和已成立訂單都還在；續訂後可繼續新增預約。`

提示必須在真正受限的動作前出現，並同時說明「哪些仍可使用」；不得登入後立刻用整頁
遮罩恐嚇，也不得把試用寫成「免費」卻在未揭露時限後扣款。

### 9.6 正式上線前仍需 Owner 拍板

- 免費／試用採天數、有效旅客數、有效訂單數或已發布有效行程數，以及各自的實際上限。

- 團隊席次階梯與超額席次價格。
- 取消後原設定可立即恢復的保證天數，以及各類資料的封存、匿名化與刪除期限；法規或付款帳務要求較長者以較長者為準。在期限拍板前不得因方案到期自動刪除資料。
- Midao 上架費與平台代建服務的計價方式。
- LINE 額度與進階自動化的付費邊界；不得改動本節列出的免費基礎通知。

在這些數字拍板前，只能使用測試旗標、UI 原型與匿名化事件驗證，不得修改 Production
價格、啟動真實訂閱扣款或對外宣稱正式方案已上線。
